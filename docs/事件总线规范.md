# 《事件总线规范》

| 项 | 内容 |
|---|---|
| 命名模板 | `dsh-training:<board>:<action>` |
| 注册表 | `packaging/contracts/events.json`（**唯一事实来源**） |
| 传输层 | 进程内 EventBus（插件 `ctx` 事件），关键事件可选落盘日志 |
| 校验 | `packaging/scripts/check-boards.mjs`（每个板块 `events` 字段对注册表） |

---

## 1. 为什么先定命名

五大板块（任务接发 / 工作台 / 社区 / 协作分组 / 控制面板）会大量联动：
任务完成 → 金币结算 → 等级提升 → 仪表盘刷新 → 角色播动作。
如果事件名各处随便起，后期就是一团乱麻。所以：

**事件名 = `dsh-training:` + 发出板块 id + `:` + action（kebab-case）**，且 action 必须在注册表里登记过。

## 2. 命名规则

```
dsh-training:tasks:task-completed
└────┬─────┘ └──────┬────────┘ └─────┬─────┘
   命名空间      板块 id（必须已注册）   action
```

| 规则 | 说明 |
|---|---|
| 前缀固定 | `dsh-training:` |
| 板块段 | 必须等于某个已完成注册的 `board.json` 的 `id` |
| action | `^[a-z][a-z0-9]*(-[a-z0-9]+)*$`，动词过去式或名词短语 |
| 禁止 | 无归属事件、action 带参数/冒号/大写、同一语义两种拼法 |
| 板块自报 | `emits` 用**短 action**（`task-completed`），`consumes` 用**完整名**（`dsh-training:core:level-up`），基座会容忍短名并自动补前缀 |

## 3. 事件信封

```json
{
  "v": 1,
  "id": "018f3c2e-...",
  "at": "2026-10-24T12:00:00.000Z",
  "source": "tasks",
  "type": "dsh-training:tasks:task-completed",
  "subject": { "taskId": "t-001", "userId": "u-01" },
  "payload": { "score": 12, "coins": 30 },
  "correlationId": "c-7f3a"
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `v` | ✅ | 信封版本，当前 `1` |
| `id` | ✅ | 唯一，用于消费幂等去重 |
| `at` | ✅ | ISO 时间 |
| `source` | ✅ | 发出板块 id |
| `type` | ✅ | 完整事件名 |
| `subject` | ➖ | 业务主体 id（谁） |
| `payload` | ✅ | 业务数据（只放值） |
| `correlationId` | ➖ | 串联同一条业务链路 |

**五条铁律**

1. `payload` 必须可 JSON 化：不放函数、循环引用、文件句柄、Date 对象（用 ISO 字符串）；
2. **消费方必须幂等**：按 `id` 去重，重复投递不产生二次副作用；
3. 发布方**不等待**消费方；消费失败写 `dead-letter.jsonl`（含 `type`/`id`/错误栈），不阻塞发布；
4. 顺序只在**同一 source 内**保证；跨 source 不保证先后；
5. 兼容性：新增字段必须可选；删字段/改语义 = 升 `v`。

## 5. 主链路（可运行的整体）

```
1. dsh-training:tasks:task-accepted   ← 发起人验收通过
2. dsh-training:core:settlement-requested          ← 请求结算
3. dsh-training:tasks:reward                      ← 赏金结算请求（本板块只发事件）
4. dsh-training:core:settlement-done               ← 结算完成
4. dsh-training:core:coins-changed                 ← 金币变动
5. dsh-training:core:level-up                      ← 触发升级
6. dsh-training:feature-console:dashboard-invalidate  ← 仪表盘作废重绘
7. dsh-training:character-txzf:action-request      ← 角色播结算动作
```

链路由 `packaging/contracts/events.json` 的 `chains` 字段记录，测试可据它做"链路完整性"断言。

## 6. 实现约定（进程内 EventBus）

| 关注点 | 约定 |
|---|---|
| 发布 | 板块内 `bus.emit(envelope)`，`type` 必须来自注册表 |
| 订阅 | 板块声明 `events.consumes`，只在声明范围内订阅 |
| 幂等 | 消费端维护 `seen: Set<id>`（有界 LRU，默认 2000 条） |
| 死信 | 失败写 `%LOCALAPPDATA%\dsh-training\dead-letter.jsonl`，字段 `{at,type,id,error}` |
| 日志 | `DSH_TRAINING_EVENT_LOG=1` 时把事件写到 `event-log.jsonl`（排查联动用） |
| 禁写业务 | `feature-console` 只做聚合刷新，不得回写业务数据（避免环） |

## 7. 新增事件的流程

1. 在 `contracts/events.json` 的 `byBoard.<板块>` 里加 action；
2. 在板块 `board.json` 的 `events.emits`（或 `consumes`）里声明；
3. 跑 `node packaging/scripts/check-boards.mjs --all`；
4. 若属于跨板块联动，把链路补进 `chains`。

> 没登记就来路不明的事件名，`check-boards` 会直接判失败——**这是故意的**。
