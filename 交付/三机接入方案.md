# 三机接入方案（dsh-2 / dsh-3 状态进钉钉群）· 待总控点头

| 项 | 内容 |
|---|---|
| 依据 | 总控令 R-237 第四条：B/C 与 dsh-2/dsh-3 通道由我设计并实施，**先出一页方案发群，点头后动手** |
| 目标 | 三机状态（做了什么/卡在哪）能直接进钉钉群，**不依赖人工转达** |
| 现状 | 只有本机 dsh 有推送能力；dsh-2/dsh-3 完全不可见（这也是今日汇总两栏只能写"未报到"的原因） |
| 密钥纪律 | webhook / token 只落各机**本机文件**，不入群、不入文档、不入代码库 |

---

## 方案 A（推荐）：**共享同一机器人 + 各机自报**

```
dsh ─┐
dsh-2 ├─→ 同一个钉钉群机器人 webhook ─→ 群
dsh-3 ┘        （各机本地 im.json，权限最小）
```

| 项 | 设计 |
|---|---|
| 分发内容 | 每机一份「接入包」：`scripts/machine-report.mjs` + `data/im.json`（含 webhook+secret，**本机文件**） |
| 每机行为 | 每天 09:00 / 21:00 各发一行：`[dsh-2] 做了什么 / 卡在哪`（脚本自动采集 git HEAD、最后提交、在跑任务数） |
| 密钥风险 | webhook 复制到 3 台=**任意一台泄露即可发群**。缓解：机器人安全设置保留「加签」；发现异常由我更换 secret 并重发接入包 |
| 需要总控点头 | ① 是否允许同一 webhook 分发到 B/C 两台；② 是否允许在两台装 Node 脚本（约 10 KB，无需额外依赖） |
| 我的实施成本 | 每台 3 分钟（发文件 + 跑一次自检）；总计 <15 分钟 |

**优点**：无需网络互通、无中间服务、失败隔离（一台挂了不影响另两台）。
**缺点**：三份密钥副本（但都在各自本机）。

---

## 方案 B：**本机作 Hub，两机上报**

```
dsh-2 ─HTTP POST─┐
                 ├─→ dsh（本机 :19500 收集器）─→ 汇总后发群
dsh-3 ─HTTP POST─┘
```

| 项 | 设计 |
|---|---|
| 前置 | 三机需**网络互通**（同内网/可路由），且 dsh 本机端口可被访问 |
| 优点 | 密钥只有一份（只在本机）；汇总格式统一由我控制 |
| 缺点 | 依赖内网可达；dsh 关机则全线断；需开端口（安全面扩大） |
| 适用 | 三机确实在同一内网 |

---

## 方案 C：**各机各建自己的机器人**

| 项 | 设计 |
|---|---|
| 做法 | 每台建独立机器人（三套 webhook/secret），各发各的 |
| 优点 | 密钥完全隔离，一台泄露不影响其他 |
| 缺点 | 需在三台各做一次钉钉建机器人（**属人工 SMS/扫码环节**，与"人不动手"冲突）；群消息来源分散 |
| 结论 | 不推荐（违反 R-237 精神） |

---

## 我的建议与请求

**建议 A**，理由：零网络依赖、实施 <15 分钟、失败隔离；密钥暴露面用「加签 + 定期轮换」控制。

**请总控点头两件事**（回"批准 A"即可）：
1. 允许把同一群机器人 webhook 分发到 dsh-2 / dsh-3（各自本机文件）。
2. 允许在两台放置 `machine-report.mjs` 并配置每日 09:00 / 21:00 定时（Windows 计划任务，需两台管理员权限）。

**点头后我的动作**（30 分钟内）：
1. 生成接入包（脚本 + 配置模板，webhook 单独给，不进群）；
2. 逐台安装并跑自检（发一条 `[dsh-2] 接入自检 OK`）；
3. 群内发"三机接入完成"公告，附三机首条自报截图（我截的是 CLI 回执，群画面由总控补）；
4. 明早 09:00 起三机各自自动上报。
